\chapter{多模态数据合成框架}

\section{背景}
当前多模态大语言模型（Multimodal Large Language Model, MLLM）的训练正面临“\textbf{数据质量而非数据数量}”成为主要瓶颈的阶段性转折。正如第1章所指出的，能力上限越来越受制于训练信号的\textbf{质量、对齐与推理密度}：互联网抓取的图文对普遍存在噪声大、语义对齐弱（Misalignment）、图像质量参差不齐（水印、模糊）等问题；而人工标注虽可靠，却成本高且难以覆盖长尾场景、复杂交互形态与多步推理链路。更关键的是，真实落地任务中暴露出的误差往往具有“结构性”——模型可能\textbf{看不清/定位不稳}（小目标与文字细节）、\textbf{绑不牢}（视觉证据与语言描述对应松散）、\textbf{想不全}（需要先识别再推断的任务易短路或幻觉）。因此，提升 MLLM 能力的关键不在于盲目扩规模，而在于能否持续产出\textbf{高信息密度、高对齐度与高推理密度}的数据\citep{chen2023sharegpt4v,xu2024mmevol,liu2025synthvlm}。

前两章的两条任务主线进一步把这一瓶颈“落到可操作的工程问题”上：在 GUI 场景（第\ref{chap:gui}章）中，UI Agent 要求模型在控件密集、文字细小且状态易变的界面中完成 Referring/Grounding 等\textbf{可执行的像素级对齐}，数据必须同时提供\textbf{紧致 bbox、OCR 对齐、关系/状态约束}并可自动质检；在世界知识场景（第\ref{chap:world_knowledge}章）中，模型需要将图像中的\textbf{具体实例}锚定到知识空间中的\textbf{抽象实体与事实}，并在条件约束下完成\textbf{先识别再推理}的链路，数据必须保证\textbf{对齐可验证}并尽可能提供\textbf{过程性约束}以避免短路学习。两类实践在差异中形成互补：GUI 强调\textbf{精度与可执行}，世界知识强调\textbf{对齐可信与推理贯通}；但二者也揭示了多模态数据合成的共通骨架——\textbf{数据源组织}、\textbf{结构化初始化}、\textbf{任务分解与生成}、\textbf{增强/过滤与多维校验}、以及\textbf{失败回流与闭环迭代}。

在第\ref{chap:gui}章（感知端）与第\ref{chap:world_knowledge}章（推理端）两端实证的基础上，本章把研究路径从“\textbf{如何在两端做好数据工程}”推进到“\textbf{如何把两端的共通骨架抽象为统一框架}”，并进一步将该框架实例化到光谱的\textbf{综合中段}（GUI CUA），通过端到端 SFT 实验给出量化证据，从而在方法学层面闭合两端工作并验证其跨任务可迁移性。具体而言，本文提出\textbf{Auto-Evol}多模态数据合成框架：将“合成数据生成”从单步的“图$\rightarrow$文/问答”升级为一个包含\textbf{正反双向链路}、\textbf{任务导向的原子问题生成}、\textbf{代理式生成与进化增强}、\textbf{多维校验与闭环反馈}的工程系统。该框架吸收并统一了 ShareGPT4V、MMEvol、SynthVLM、Synthesize Step-by-Step 等工作中可复用的关键组件\citep{chen2023sharegpt4v,xu2024mmevol,liu2025synthvlm,li2024synthesize}，并以第\ref{chap:gui}章与第\ref{chap:world_knowledge}章的\textbf{数据合成方法}为起点，抽象总结出一套\textbf{可落地、可迭代、可验证}的多模态数据合成方法学，为后续在更多任务域中复用与扩展提供统一底座。

\section{构造框架}
图\ref{fig:auto_evol_pipeline}给出了Auto-Evol框架的闭环结构。该框架从数据源侧同时接入\textbf{原生图片}与\textbf{生成图片}两类输入，通过数据初始化统一格式并沉淀生成所需的源信息（可包含自动/人工标注产物），随后进行质量过滤；再将样本路由到“任务导向的原子问题生成”，并按感知、理解、推理三类代理生成多任务指令；最后通过数据增强与数据校验提升多样性、难度与正确性，若校验不过则回流重写/重生成，最终产出可用于监督微调（SFT）与后训练（Post-training）的高质量合成数据。

\subsection{构造流程}
\paragraph{（1）数据源：原生图片与生成图片的双向数据流}
Pipeline顶部同时接入两类数据源：
\begin{itemize}
  \item \textbf{原生图片（真实收集）}：来自真实应用截图、公开数据集与搜索收集的高清图片。GUI章使用真实设备分辨率截图以保留小控件细节；世界知识章以“词条$\rightarrow$图片”的方式确保实体可控。
  \item \textbf{生成图片（Text-to-Image）}：当长尾场景稀缺或需要严格对齐时，可采用“文本$\rightarrow$图像”的反向数据工程。SynthVLM表明，先清洗caption再用扩散模型生成高分辨率图像，并用CLIPScore+SSIM筛选，可从源头提高图文对齐度与图像清晰度，从而以更少数据达到更强效果\citep{liu2025synthvlm,hessel2021clipscore,wang2004ssim}。
\end{itemize}
双向数据流的价值在于：\textbf{正向数据流（图$\rightarrow$文）}擅长覆盖真实分布，\textbf{反向数据工程（文$\rightarrow$图）}擅长制造“强对齐、可控分布”，两者互补可显著提升数据的覆盖与可信度。

\paragraph{（2）数据初始化：统一格式与任务路由的前置条件}
“数据初始化”的核心目标是将不同来源的原始材料整理为后续\textbf{指令/QA生成}阶段可直接\textbf{提取或参考的源信息池}：包括可追溯的元信息（来源、分辨率、类别/词条等）、必要的路由标签，以及与任务相关、可被复用的结构化线索。这里的“源信息”不要求跨数据源完全同构，而是强调\textbf{为生成提供可依赖的参照物}。在实践中，初始化阶段通常会沉淀两类关键产物：
\begin{itemize}
  \item \textbf{自动生成的结构化描述/要素（用于蒸馏的中间表征）}：以世界知识数据为例，初始化阶段往往会先为图片生成结构化caption，并显式区分“画面可见信息”（主体、属性、关系、时空线索等）与“背景知识要点”（年份、导演、题材、所属系列等可核验事实）。该caption随后既可用于图文相关性过滤，也可作为知识要素抽取与RecQA/KnowQA/FinalQA构造时的主要上下文依据，从而把“图像与知识源”转化为可复用、可校验的中间表征。与此同时，为提升大模型蒸馏的可靠性，caption/要素抽取常配套引入：固定输出格式与字段约束（例如先给出实体识别结论，再给出若干可核验事实）、自一致性采样/多次生成投票、以及“生成--判别”式复核（judge过滤不一致或缺乏证据支撑的内容），将不确定与幻觉样本在数据侧前置淘汰。以词条“\emph{1917}（电影）”为例，caption会被要求同时给出图中“士兵/军装/战场环境”等可见证据与“2019、萨姆·门德斯、战争片”等知识要点；随后系统依据caption与词条的一致性保留高相关样本，并据此生成识别锚定的RecQA与需要知识调用/筛选的KnowQA、FinalQA。
  \item \textbf{人工标注与上下文采集（高置信锚点）}：人工标注适用于\textbf{需要像素级精确度}、\textbf{存在强歧义/同名消歧}、或\textbf{需要遵循严格规则与一致性约束}的场景，其作用是为后续生成提供稳定锚点与可复核依据。以GUI任务为例，可沉淀候选控件集合、紧致bbox、OCR文本、控件可交互性/状态（如Activated/Interactable/Filled）以及标签--控件绑定等关系信息，从而支撑Grounding/Referring等任务的可执行监督；以世界知识任务为例，可对词条集合进行边界校正与别名对齐、处理同名实体歧义，并对关键样本进行抽检复核，确保“图片$\leftrightarrow$词条$\leftrightarrow$知识”的对应关系可追溯、可验证。
\end{itemize}

\paragraph{（3）过滤：相关性与准确性的第一道闸门}
“过滤相关性、准确性”是合成数据可用性的核心保障，其目标是尽早剔除“错图错标/弱对齐/不可验证”的样本，避免噪声在后续指令生成与训练中被放大。以第\ref{chap:world_knowledge}章为例，图片来自自动检索，天然会混入同名歧义、相似实体、无关插图等噪声；因此在进入QA构造前，系统会基于“图片$\leftrightarrow$词条”的匹配强度进行\textbf{相关性评分}（1--5分），并要求输出简要理由与固定格式，便于程序解析与自动化处理。在阈值化过滤的同时，为兼顾覆盖率与长尾，流程通常会保留高分样本并对部分中等分样本进行抽样复核，从而在“尽可能保留潜在相关证据”与“抑制错配监督”之间取得平衡。

与之相比，SynthVLM更偏向使用\textbf{自动指标}（如CLIPScore、SSIM等）对图文对齐度与图像质量进行强筛选\citep{liu2025synthvlm,hessel2021clipscore,wang2004ssim}，其优势在于可规模化、可重复；而世界知识任务中的相关性过滤更强调\textbf{语义一致性与可解释性}（尤其是同名消歧与实体锚定）。两者共同指向同一结论：过滤不仅是去噪，更是\textbf{控制训练信号可信度与信息密度}的关键环节。

\paragraph{（4）任务导向的原子问题生成（三基础能力/三生成链路）}
在Auto-Evol中，“\textbf{把任意多模态任务统一分解为感知、理解、推理三类基础能力，并为每一类能力设计对应的数据生成链路与监督信号}”。因此，三代理生成不仅是工程上的分工，更是多模态模型能力结构的抽象——其他任务数据（如GUI定位与交互、世界知识识别与问答、多轮对话、工具调用等）都可以视为三类能力的组合与不同权重的路由结果。

具体而言，Pipeline中的三条生成链路可概括为：
\begin{itemize}
  \item \textbf{感知链路（Perception）}：以图像为主要证据，生成可\textbf{直接对齐到视觉区域/实体}的监督信号（如bbox、OCR文本、实体识别锚定）。例如在GUI中，感知链路产出紧致bbox与文本对齐，使模型学会在密集小控件场景下稳定“指哪打哪”；在世界知识中，感知链路对应RecQA：先把图片中的具体实例可靠地锚定到词条实体，解决“看见但叫不出名字/叫错名字”的问题。
  \item \textbf{理解链路（Understanding）}：在感知锚点基础上，生成\textbf{高密度语义解释}与可复用上下文（如结构化caption、关系解释、背景知识片段），提升语义覆盖与可解释性。以世界知识为例，初始化阶段沉淀的结构化caption把“画面可见信息”与“背景知识要点”组织成稳定上下文，理解链路据此构造KnowQA，将可泛化的事实知识与实体绑定；以GUI为例，理解链路对应Referring类数据：给定bbox输出控件功能/文本/属性及其与周边元素的关系，从而让模型学会“看懂”而不仅是“定位”。
  \item \textbf{推理链路（Reasoning）}：在“感知锚定 + 语义/知识上下文”之上，生成需要\textbf{多步条件推断}的监督信号，并尽可能加入过程性约束以避免短路学习。以世界知识为例，FinalQA要求模型先识别实体再调用知识完成筛选/推断，并在加入Think/CoT后显著提升推理指标，说明推理链路必须提供“先识别再推理”的过程监督；以GUI为例，推理链路对应包含多步计划与工具调用约束的任务数据，使模型学习在页面状态、控件关系与目标约束下生成可执行的动作序列。
\end{itemize}
通过上述三链路路由，Auto-Evol把“难任务”拆成“可控生成、可控校验”的组合单元：感知链路提供可对齐的锚点，理解链路提供可复用的语义/知识上下文，推理链路提供过程性约束与可验证推断，从而系统性降低错配与幻觉传播，并提升数据的可迁移性与覆盖度。

\paragraph{（5）数据增强：细粒度、难度、指令多样性的系统注入}
Pipeline中的“数据增强”可理解为对训练信号的三条系统性“加密”方向，它们既对应数据侧要解决的三类瓶颈，也对应模型希望被强化能力，即关注细节、攻克难题、与人交互的能力：
\begin{itemize}
  \item \textbf{细粒度增强（对齐粒度 $\rightarrow$ 感知能力）}：针对多模态数据常见的“对齐粒度不够/忽略长尾细节”问题，围绕图像中的次要物体、背景细节与空间关系补充监督，使模型学习到更细的视觉证据与文本描述之间的对应关系。MMEvol的\emph{Fine-grained Perception Evolution}提供了一个可操作框架\citep{xu2024mmevol}：利用检测框等视觉约束，将问题生成从“主目标描述”扩展到“被忽略区域/长尾物体”的定向提问，从而减少“看见但不说/说错”的幻觉风险。对应到本文任务中，GUI场景的小控件与小字体天然属于细粒度信息，补充紧致bbox与OCR对齐监督，本质上就是对感知链路的信息密度加密。
  \item \textbf{难度增强（推理密度 $\rightarrow$ 推理能力）}：针对“指令复杂性不足/缺乏深度推理步骤”的问题，通过多步推理、条件约束与可执行步骤显式提升推理密度。例如可以将推理抽象为“视觉操作链”（如定位、OCR、存在性判断、计数/计算等原子操作），并要求在输出答案前生成可追踪的推理步骤，从而把“难题”转化为可校验的过程监督。本文在世界知识任务中对FinalQA加入Think/CoT（要求先识别实体，再调用知识完成筛选/推断），并在实验中观察到推理指标显著提升，正体现了“过程性推理监督”对推理能力增强的关键作用。
  \item \textbf{指令多样性增强（交互覆盖 $\rightarrow$ 理解与指令遵循能力）}：针对“指令形式单一/交互覆盖不足”的问题，将同一语义目标改写为多样化的交互形式（如结构化JSON、代码片段、角色设定、多轮对话等），以提升模型对不同用户表达与输出约束的鲁棒性。MMEvol的\emph{Interaction Evolution}强调在保持视觉约束的前提下扩展输出格式与交互方式\citep{xu2024mmevol}，避免仅做“文本复杂化”而脱离图像证据；在Auto-Evol中，该方向对应理解链路的格式多样化注入，使模型既学会“说对”，也学会“按要求说”。
\end{itemize}

\paragraph{（6）数据校验：LLM-as-a-Judge + 工具/执行校验的多维验证}
高质量合成数据必须“可验证”。更准确地说，\textbf{数据校验就是对数据做评测}：围绕“我们希望模型最终具备什么能力”，反向定义数据应满足的作用与特性，并在生成后用可操作的评测准则筛选与修正数据分布。总之想要什么样的数据，就要用对应方法校验才能得到，例如这三类比较普遍的校验：
\begin{itemize}
  \item \textbf{难度校验（过滤“过于简单”的样本）}：若目标是让模型解决难题，则需要避免训练集中被大量“简单题”稀释。实践中可用\textbf{能力较弱的模型}或规则基线先行作答：若弱模型在不依赖关键视觉/知识证据的情况下即可轻易答对，则该样本更可能属于低难度或存在捷径，可降权、剔除或重写以提升推理密度。
  \item \textbf{正确性与可验证性校验（确保监督信号“对”）}：若目标是让模型切实学会某项能力，则监督必须可靠。可用\textbf{更强的模型}进行一致性复核（例如答案唯一性、推理链条自洽、与图像证据相符），并对推理类样本引入\textbf{工具/执行校验}（如代码执行、规则验证、可解析约束检查）来验证最终答案与中间步骤的一致性，从源头抑制错误监督与幻觉传播。
  \item \textbf{覆盖与多样性校验（保证可泛化的交互学习）}：若目标是提升交互与指令遵循鲁棒性，则数据需要在任务类型、表达方式与输出格式上足够多样。可通过分布统计与约束检查（任务路由占比、模板去重、格式合法性、长尾覆盖等）评估并调整数据，使模型既学会“答对”，也学会“按要求答”。
\end{itemize}

\paragraph{（7）回流重写/重生成：闭环提升与分布自适应}
当某类任务通过率持续偏低时，系统触发右侧“重写”回路：要么对指令/答案进行重写（保持图像不变），要么回流到“生成图片”分支重新合成更契合任务的图像，再进入流程。该闭环使数据系统具备“自我修复”的能力，避免一次性生成导致的质量不可控的同时也不要浪费以得倒的信息。

\subsection{从两类任务实践到统一框架的归纳}
如前文所述，当前多模态模型能力上限越来越受制于训练数据的\textbf{质量、对齐与推理密度}，并在真实落地中呈现出一系列“结构性”误差模式：例如对小目标与文字细节不稳定、视觉证据与语言描述绑定松散、以及在“先识别再推断”的任务上易出现短路映射或幻觉。对应这一瓶颈，本文采用“\textbf{从精细可执行监督到可控推理监督，再到统一框架抽象}”的递进路线：先在GUI任务中用强约束、可执行的像素级监督打牢感知与定位基座，再在世界知识任务中引入可验证对齐与过程性推理监督贯通“识别$\rightarrow$知识$\rightarrow$推断”，最终将两类实践中可复用的模块上升为统一的数据合成方法学。

需要强调的是，Auto-Evol并非“从概念出发”的抽象框图，也不只是对两章工作的事后总结，而是建立在\textbf{系统性相关工作调研}与\textbf{本文多模态数据/训练实践}之上的方法学抽象：一方面，ShareGPT4V、SynthVLM、MMEvol、Synthesize Step-by-Step等工作分别从高密度对齐、反向数据工程、进化式增强与过程可执行推理等角度提供了可复用的模块化思想\citep{chen2023sharegpt4v,liu2025synthvlm,xu2024mmevol,li2024synthesize}；另一方面，本文在GUI与世界知识两类高难任务的落地过程中沉淀了关于多源数据组织、结构化初始化/标注、中间表征、过程性监督与质控的工程经验。下面以两条主线作为代表性实例说明该框架的归纳来源：
\begin{itemize}
  \item \textbf{GUI主线（第\ref{chap:gui}章）}：以\textbf{结构化初始化}与\textbf{细粒度标注}为核心，将“截图”转化为可计算、可追溯的控件集合（bbox、OCR、状态向量、关系图谱），再围绕Referring/Grounding等任务生成可执行监督，并通过多源融合与质控迭代提升稳定性。该方法很好解决了“\textbf{小目标/文字细节不稳定}”与“\textbf{语义--几何绑定松散}”等结构性问题：用强约束的像素级锚点把模型输出绑定到可执行目标，强调“\textbf{可执行定位}”与“\textbf{可解释语义}”的双对齐，并体现了细粒度对齐与分层能力路由在复杂交互场景中的必要性。
  \item \textbf{世界知识主线（第\ref{chap:world_knowledge}章）}：以\textbf{实体锚定}与\textbf{知识注入}为核心，通过“词条$\rightarrow$图片$\rightarrow$caption$\rightarrow$相关性过滤$\rightarrow$RecQA/KnowQA/FinalQA”建立从知识源到可学习多模态监督的转化链路，并通过\textbf{带推理过程（Think/CoT）的FinalQA}强化“先识别再推理”的可迁移推理策略。该方法针对“\textbf{短路映射/幻觉}”与“\textbf{推理链路缺失}”等问题：以caption作为可依赖中间表征提升可验证性，以分数化对齐过滤抑制错配噪声，并用过程监督把推理从黑箱答案转为可学习的链路，从而强调“\textbf{可验证对齐}”与“\textbf{推理链路贯通}”。
  \item \textbf{跨任务复用的工程实践（本文其他多模态工作）}：除上述两类任务外，本文在多模态数据构造与训练中还沉淀了可跨任务复用的通用做法，例如：以统一的“源信息池”承接不同数据源与标注形态、以三基础能力链路统一组织监督信号、以及以“难度/正确性/覆盖多样性”为目标对数据进行评测式校验。这些实践与调研结论共同促成了Auto-Evol作为统一框架的可迁移性与可扩展性。
\end{itemize}
综上，GUI与世界知识两条主线在“任务形态”上差异显著，但其共同结构恰好对应Auto-Evol的闭环：\textbf{数据源组织}决定覆盖与可控性（真实收集与生成/反向对齐互补），\textbf{结构化初始化}沉淀可复用的源信息与锚点（如控件集合或caption中间表征），\textbf{原子化任务拆解与路由}把复杂能力分解为感知/理解/推理三类可监督单元（如Referring/Grounding或RecQA/KnowQA/FinalQA），\textbf{代理式增强}提升信息密度与难度分布，\textbf{多维过滤/评测式校验}在数据侧前置约束正确性与可验证性，并通过\textbf{回流重写/重生成}将失败样本转化为下一轮迭代目标。由此，Auto-Evol回答了第1章提出的核心问题：将“零散的一次性合成”升级为\textbf{可控、可评测、可迭代}的数据合成系统，使高信息密度、高对齐度与高推理密度的训练信号能够稳定产出与跨任务复用。

\section{模块有效性验证}
Auto-Evol的关键模块并非凭经验堆叠，其必要性可在第4章与第5章的实验结果中得到直接验证。下面从“模块$\rightarrow$证据”的角度进行归因式总结。

\paragraph{（A）多源融合与结构化监督的必要性（对应初始化（含标注）/过滤）}
在GUI任务中，仅靠基线模型性能较低；引入开源清洗数据后指标显著提升，而进一步融合闭源精标数据后提升更为明显：如表\ref{tab:gui_data_ablation}所示，Grounding F1由0.324提升至0.846，Referring F1由0.523提升至0.905。该结果表明，\textbf{多源覆盖 + 结构化标注 + 质控}能够显著提高定位与理解的稳定性，是Auto-Evol“数据初始化--协作标注--过滤”的直接实证。

\paragraph{（B）中间表征与相关性过滤的必要性（对应caption与对齐校验）}
在世界知识任务中，caption不仅提供“更丰富的描述”，更作为可依赖的中间表征支撑相关性过滤与后续QA构造。实验一的结论指出：\textbf{Image Caption对识别显著有益}（表\ref{tab:wk_ablation_part1}），说明“中间表征 + 对齐筛选”能够为实体锚定提供更稳健的训练信号，对应Auto-Evol中“过滤相关性、准确性”与“相关性校验”的设计动机。进一步地，第\ref{chap:world_knowledge}章在图文相关性过滤环节给出量化证据：在随机抽取的2000条“图片--词条”样本上，若仅做相关/不相关二分类过滤，最终保留约1009条；引入基于caption的1$\sim$5相关性分数并保留$\ge$3分样本后，可保留约1511条，同时“几乎无幻觉”样本占比由72.6\%提升至80.3\%，且“大部分幻觉”占比由7.9\%降至4.2\%（表\ref{tab:wk_rel_filter_hallu}）。这表明：caption作为中间表征不仅提升了对齐判别的可解释性，也使分数化过滤能够在\textbf{覆盖率}与\textbf{对齐可靠性}之间取得更优平衡，从而为后续RecQA/KnowQA/FinalQA提供更干净的实体锚点与知识上下文。

\paragraph{（C）显式推理过程数据对推理能力的显著增益（对应原子化/推理代理/执行校验）}
第\ref{chap:world_knowledge}章进一步揭示：仅监督最终答案的FinalQA可能诱发“短路映射”，导致推理指标提升不显著甚至下降；而当FinalQA加入简要推理过程（Think/CoT）并扩充数据分布后，final相关指标\textbf{出现显著提升}。如表\ref{tab:wk_think_improve}所示，在Chinese SimpleVQA上，\texttt{Ovis2.5\_9B\_think\_part123}相对\texttt{qwen2.5-VL-7b}在F1\_Final上提升11.9个点（同时F1\_Rec提升16.1个点），验证了“\textbf{显式推理链路监督}”对可迁移推理能力的关键作用。这一现象与Auto-Evol强调的“原子化任务拆解 + 推理代理生成 + 多维校验（含可执行/一致性校验）”相一致：通过过程性监督与可验证机制，才能在提升推理强度的同时抑制幻觉与短路学习。

\section{Auto-Evol在GUI CUA领域的实例化}
\label{sec:auto_evol_gui_cua}

\paragraph{GUI CUA 与第\ref{chap:gui}章 GUI 的本质差异：从感知端到综合中段}
尽管同属“GUI”大类，CUA 任务在监督形式上与第\ref{chap:gui}章 Mobile UI 的 Referring/Grounding 存在本质区别：
\begin{itemize}
  \item \textbf{第\ref{chap:gui}章 GUI（感知端）}：单步、静态、像素级的 Referring/Grounding 监督，模型只需在\textbf{一张截图}上完成“指代识别”或“定位落地”，监督粒度为 bbox / OCR / 状态向量；
  \item \textbf{第5章 GUI CUA（综合中段）}：\textbf{多步、动态、可执行}的操作链监督，模型需要在\textbf{动态变化的桌面环境}中完成“感知当前状态 $\rightarrow$ 规划下一步动作 $\rightarrow$ 执行 $\rightarrow$ 跟踪状态转移”的完整闭环，监督粒度为\textbf{完整轨迹 + 可执行真实结果比对}。
\end{itemize}
因此，GUI CUA 实例化\textbf{并非第\ref{chap:gui}章 GUI 工作的简单延伸}，而是 Auto-Evol 框架\textbf{从感知端跨越到综合中段}的真正迁移验证：它同时考验框架对\textbf{感知能力（控件状态识别）+ 推理能力（多步规划）+ 过程性监督（状态机校验）}三类需求的协同支撑。配合第\ref{chap:gui}章（感知端）与第\ref{chap:world_knowledge}章（推理端）的工作，三者共同覆盖数据能力光谱的两端与中段，形成对 Auto-Evol 框架可迁移性的完整证据链。

为进一步验证Auto-Evol框架在更复杂多模态场景下的可迁移性与可扩展性，本文以该框架为方法学，在GUI计算机使用智能体（Computer Use Agent, CUA）领域提出了一个面向\textbf{可验证任务合成}的工程实例。该实例选取OSWorld\citep{xie2024osworld}评测体系作为载体，覆盖三个典型LibreOffice应用domain（Calc电子表格、Impress演示文稿、Writer文字处理）以及VSCode、Chrome等扩展domain，通过Pipeline化的可验证任务自动生成系统，将“零散人工标注CUA任务”升级为“面向感知/理解/推理三类能力、可批量生产+可自动评测+可闭环迭代”的数据合成链路。与近期EvoCUA\citep{xue2026evocua}通过可验证合成扩展CUA训练经验的整体思路一致，本实例在Auto-Evol视角下更强调\textbf{数据侧的能力路由、过程性校验与跨domain复用}。

\subsection{流程概览与Auto-Evol模块对应}
该GUI CUA实例由三个外部阶段（生成--提交--审计）与八个Gate（G1--G8）组成的内部流程构成，可视为图\ref{fig:auto_evol_pipeline}的Auto-Evol闭环在CUA场景下的具象化。下文按“框架模块$\rightarrow$实例流程”逐项映射。

\paragraph{（1）数据源接入与结构化初始化 $\rightarrow$ Capability池 + Persona池 + Phase 0 Sampler}
对应Auto-Evol的“数据源”与“数据初始化”模块，在GUI CUA实例中由两个池子驱动：（a）\textbf{capabilities.json}——为每个domain显式定义的“原子能力字典”（如Calc的85个cap：F1--F35公式类、S1--S15格式类、O1--O13组织类、A1--A9分析类、W1--W6工作表类、E1--E5编辑类等），每个cap均挂有元数据（描述、所需列类型、执行优先级、互斥约束、对应OSWorld evaluator函数）；（b）\textbf{Persona池}——10万条偏向AI-exposed职业（计算机科学/数学/金融/商业/统计等）的ElitePersonas，为业务皮提供可控的人设分布。Phase 0 Sampler按链长分布（如40\%/35\%/25\%对应1/2/3链）抽取cap combo + persona，并施加mutex（互斥）/needs（依赖）约束，生成可直接进入下游Pipeline的结构化record。该步骤与Auto-Evol中“沉淀可复用的源信息池与路由标签”形成同构。

\paragraph{（2）任务导向的原子问题生成 $\rightarrow$ Phase A--C三链路}
对应Auto-Evol的“感知/理解/推理”三能力链路，在GUI CUA实例中按“业务皮--操作--评测”三段式生成：
\begin{itemize}
  \item \textbf{Phase A（TaskSpec LLM，对应理解链路）}：以persona为上下文调用LLM生成业务表述（topic / sheet\_name / columns / n\_rows / persona\_flavor等），使任务具备真实业务场景的语义外壳。Gate 1校验schema与合理性，不通过即重做。
  \item \textbf{Phase B--C（chain executability + base/GT生成，对应感知链路）}：按cap combo逐步在openpyxl / python-pptx / python-docx等真实文档对象上施加确定性变换（每个cap实现为\texttt{transform(wb, ctx) -> trace\_entry}），并通过\texttt{soffice --headless}做round-trip消除原生格式差异；最终生成base文件（agent的起始状态）与GT文件（agent应达到的目标状态）。Gate 2--3校验cap链可执行性、文件存在性以及GT与base的可见diff。
  \item \textbf{Phase D（evaluator deterministic反推，对应推理校验前置）}：在GT确定后，由代码按cap语义反推OSWorld evaluator配置（17类规则：\texttt{sheet\_data} / \texttt{check\_cell} / \texttt{check\_formula} / \texttt{style\_range} / \texttt{compare\_csv}等），\textbf{无需LLM参与}，从源头保证“评测即确定性的真值比对”，对应Auto-Evol“可执行/一致性校验”的最强形态。
\end{itemize}

\paragraph{（3）数据增强 $\rightarrow$ Phase E Instruction LLM + 多样性变体}
对应Auto-Evol“细粒度/难度/指令多样性增强”中的“指令多样性增强”维度。在GUI CUA实例中由Phase E实现：将业务皮、cap trace、GT inspect与anchor集合喂给LLM，按4种指令风格（natural\_user 50\% / specific\_request 30\% / verbose\_business 15\% / terse\_command 5\%）与3种micro-variants组合（共4$\times$3=12个prompt槽位）生成自然语instruction，使同一语义目标可被改写为多样化的交互形式。Gate 4按“schema合法 / anchor出现 / 规则一致 / LLM-judge通过”四重校验，不通过即触发重写。

\paragraph{（4）数据校验 $\rightarrow$ 8-Gate体系 + 离线evaluator模拟 + L2扰动 + 防泄漏Gate}
对应Auto-Evol中“LLM-as-a-Judge + 工具/执行校验的多维验证”，但在GUI CUA实例中进一步以“\textbf{可执行evaluator}”为核心：
\begin{itemize}
  \item \textbf{G7（GT-on-GT smoke）}：在生成的GT上跑evaluator期望reward=1.0——若不通过，说明evaluator配置自相矛盾，drop。
  \item \textbf{G8（FN-attack）}：构造“反事实agent输出”（如把GT还原为base、或施加L2扰动），期望evaluator reward=0.0——若仍通过，说明evaluator过松、存在假阴风险，drop。
  \item \textbf{G9（covers\_official anti-leakage）}：对显式标记“覆盖OSWorld官方任务”的cap，按token-Jaccard与LCS阈值过滤与官方instruction / value雷同的合成task，防止训练评测泄漏，保证合成数据在评测体系上仍具备区分度。
\end{itemize}
G7--G9合在一起，实现了“\textbf{数据生成阶段的自动评测式质控}”，与Auto-Evol强调的“评测式校验”在工程上完全对应；其本质是把“想要什么样的数据，就要用对应方法校验”的原则前推至生成阶段，避免噪声进入训练。

\paragraph{（5）回流重写/重生成 $\rightarrow$ Phase F--G + audit反馈}
对应Auto-Evol的“失败回流重写/重生成”。每一Gate失败即触发对应Phase重做或drop+resample（如Phase A schema fail $\rightarrow$ 重做A，Phase D'校验fail $\rightarrow$ drop）；所有accepted record聚合为\texttt{manifest.jsonl}与\texttt{task\_registry.csv}，再由OSWorld sandbox（vela）执行真实agent rollout，运行结果通过\texttt{audit\_<domain>.py}与LLM-as-judge生成confusion matrix与per-cap reward分布，反馈到下一轮Pipeline参数调整与cap优化。例如LibreOffice Calc实例从baseline 62\%累计提升至76\%，并在n=100 task batch上达到reward 84\%；三个LibreOffice domain均实现OSWorld官方任务的100\%覆盖率（Calc 47/47、Impress 47/47、Writer 23/23）。该闭环即Auto-Evol“以失败样本驱动下一轮迭代目标”原则在Agent场景下的具象化。

\subsection{与Auto-Evol在多模态合成场景下的差异化贡献}
相比第\ref{chap:gui}章与第\ref{chap:world_knowledge}章以“图片+caption+QA”为载体的合成场景，该GUI CUA实例在Auto-Evol统一框架下的差异化贡献体现在四点：
\begin{itemize}
  \item \textbf{从语义对齐到行为可执行}：监督信号从“对图像证据的描述/问答”扩展到“对桌面文档/界面状态的可执行操作链”，使Auto-Evol的“感知/理解/推理”三链路得以在“看--懂--做”完整闭环中验证；
  \item \textbf{从LLM判别到代码确定性校验}：通过把evaluator从GT反推为确定性规则（而非由LLM打分），实现了真正意义上的“工具/执行校验”，使G7/G8等Gate具备零LLM依赖、可重复的质控能力，显著降低了评测噪声与成本；
  \item \textbf{从单任务复用到跨domain模板复用}：通过共享\texttt{common/sampler\_v2.py}、\texttt{common/task\_registry.py}、\texttt{common/io\_utils.py}等基础设施，三个LibreOffice domain以及VSCode、Chrome等其他GUI domain可以复用同一套Pipeline骨架，仅需替换domain特定的\texttt{capabilities.json} + transformers + \texttt{evaluator\_parser}，体现了Auto-Evol作为统一框架在跨任务域上的可迁移性；
  \item \textbf{从单端验证到两端+中段全光谱覆盖}：第\ref{chap:gui}章与第\ref{chap:world_knowledge}章分别覆盖数据能力光谱的感知端与推理端，本节的 GUI CUA 实例化进一步覆盖了\textbf{感知+推理协同的综合中段}（多步操作链 + 动态状态机），使 Auto-Evol 框架在数据能力光谱的两端与中段三个代表性位置都获得了独立验证，从根本上回应了“统一框架是否仅依赖前两章实验进行归纳论证”的可迁移性疑问。
\end{itemize}

该实例从工程层面表明：Auto-Evol不仅适用于“图文/知识问答”等以LLM-as-Judge为主的多模态合成场景，亦可作为“GUI CUA可验证任务合成”的方法学，为构建大规模、可自动评测的Computer Use Agent训练语料提供可复用工程范式，并与OSWorld\citep{xie2024osworld}、EvoCUA\citep{xue2026evocua}等代表性工作形成互补与延伸。

\subsection{基于Auto-Evol合成数据的端到端训练验证}
\label{subsec:auto_evol_gui_cua_train}

为进一步验证Auto-Evol在GUI CUA实例化下\textbf{所产合成数据}对模型实际能力的提升效果，本文以前述LibreOffice三个domain（Calc/Impress/Writer）的可验证任务合成系统为数据源，开展端到端“合成数据$\rightarrow$轨迹采集$\rightarrow$SFT训练$\rightarrow$评测”实验。

\paragraph{合成数据规模与构造流程}
依托第\ref{sec:auto_evol_gui_cua}节描述的Pipeline，在三个LibreOffice domain上共生成\textbf{900条}经Gate 1--Gate 9全链路过滤的可验证任务（manifest.jsonl），随后调用指导模型（teacher agent）在OSWorld可交互Ubuntu沙箱中对每个任务执行rollout，仅保留与GT确定性evaluator比对reward=1.0的成功轨迹，最终得到\textbf{723条}高质量轨迹。考虑到长程多步轨迹直接作为监督信号易引入梯度稀释与上下文长度爆炸，本文对轨迹进行\textbf{单步拆分}：对一条长度为$T$的轨迹，将其展开为$T$个训练样本，每个样本以“该步之前的全部历史步骤”为上下文输入、以“当前步动作”为监督目标，从而保留多步规划语义的同时实现样本级精细化监督。最终得到约\textbf{3万条}单步训练数据，用于对Qwen3VL Think基础模型进行有监督微调（SFT）。

\paragraph{评测设置}
评测使用OSWorld官方的LibreOffice三个domain任务集合（Calc 47题、Impress 47题、Writer 23题，共117题），以每题确定性evaluator真实运行得分（满分1.0）累加为domain级reward总和，并将3个domain总和除以117得到overall accuracy（\%）。所有评测均在与训练数据合成同构的OSWorld可交互沙箱中执行，保证训练分布与评测分布一致。

\paragraph{实验结果}
如表\ref{tab:gui_cua_train_result}所示，经Auto-Evol合成数据训练后，Qwen3VL Think模型在三个domain上均获得显著提升，overall accuracy从\textbf{40.8\%}提升至\textbf{61.4\%}（绝对增益\textbf{+20.6 pt}）；其中Calc绝对得分增幅最大（+14.17，对应domain accuracy由23.0\%升至53.2\%），Impress与Writer分别绝对+5.89与+4.00（对应domain accuracy分别提升+12.5 pt与+17.4 pt），三个domain无回退。

\section{本章小结}
本章围绕“数据质量成为瓶颈”的现实约束，提出并系统化阐释了\textbf{Auto-Evol}多模态数据合成框架。其核心意义在于：将以往零散、一次性的合成数据生成，升级为一个\textbf{可路由、可评测、可闭环迭代}的数据合成系统，从而稳定地产出高信息密度、高对齐度与高推理密度的训练信号。

具体贡献体现在三点：\textbf{（1）统一能力视角}——以感知/理解/推理三基础能力为坐标系，把不同任务的数据需求统一到三条生成链路与可复用监督信号上，避免“为每个任务重新设计一套数据体系”；\textbf{（2）评测式质控}——将数据校验显式定义为对数据的评测，围绕难度、正确性/可验证性与覆盖多样性进行筛选与分布修正，降低错配监督与幻觉传播风险；\textbf{（3）闭环可持续迭代}——通过过滤、增强、校验与回流重写把失败样本转化为下一轮优化目标，使数据分布能够随任务瓶颈自适应演化。

框架的有效性在后续章节得到量化支撑：在GUI任务中，多源融合与结构化监督显著提升Grounding/Referring性能（表\ref{tab:gui_data_ablation}）；在世界知识任务中，引入中间表征与过程性推理监督（Think/CoT）带来推理指标的显著增益（表\ref{tab:wk_think_improve}）。在此基础上，本章\ref{sec:auto_evol_gui_cua}节进一步将Auto-Evol实例化到GUI CUA场景，基于OSWorld评测体系\citep{xie2024osworld}构建可验证任务合成的工程系统，并通过LibreOffice三个domain与VSCode/Chrome等扩展domain完整验证了框架在“看--懂--做”闭环下的可迁移性，与EvoCUA\citep{xue2026evocua}等代表性工作形成互补；其端到端训练验证（第\ref{subsec:auto_evol_gui_cua_train}节，表\ref{tab:gui_cua_train_result}）进一步表明，基于本框架生成的900合成任务$\rightarrow$723成功轨迹$\rightarrow$3万条单步训练数据可将Qwen3VL-Think在OSWorld LibreOffice三个domain上的overall accuracy由40.8\%提升至61.4\%（+20.6 pt绝对增益），从端到端训练角度直接印证了“可验证任务合成”对模型实际能力提升的有效性。

因此，Auto-Evol 在本论文中具有\textbf{双重定位}：（i）作为\textbf{方法论闭合}——对第\ref{chap:gui}章（感知端）与第\ref{chap:world_knowledge}章（推理端）两条主线的数据工程实践进行系统性归纳与抽象，沉淀可复用的统一闭环 Pipeline；（ii）作为\textbf{独立端到端贡献}——通过 GUI CUA 实例化在数据能力光谱的\textbf{综合中段}提供独立的可验证任务合成 Pipeline 与 +20.6 pt 的端到端 SFT 量化证据（详见第\ref{subsec:auto_evol_gui_cua_train}节、表\ref{tab:gui_cua_train_result}），证明框架确实可跨越“感知端 $\rightarrow$ 综合中段”完成迁移而非仅做归纳总结。两个定位互不替代：方法论闭合强调\textbf{统一性}（横跨两端的共通骨架），独立端到端贡献强调\textbf{迁移性与可验证性}（在新场景上的独立实验证据）。在此双重定位下，Auto-Evol 同时为第\ref{chap:gui}章与第\ref{chap:world_knowledge}章提供数据工程底座，也为后续扩展到更多多模态场景（无论位于能力光谱何处）提供了可复用的框架。
