\chapter{面向用户图形界面的视觉语言模型能力提升}
\label{chap:gui}

如第\ref{chap:intro}章所述，本文沿\textbf{数据能力光谱}三个代表性位置（感知端 / 推理端 / 综合中段）展开“两端实证 $\rightarrow$ 共通抽象 $\rightarrow$ 综合中段端到端验证”的研究路径。本章是该路径的第一站——\textbf{感知端实证}：以图形用户界面（Graphical User Interface, GUI）任务为载体，回答“在控件密集、文字细小、状态易变的场景下，如何把数据做到精细到像素、对齐到字段、绑定到状态”。该问题的答卷将在后续第\ref{chap:world_knowledge}章（推理端世界知识任务）的另一端实证形成对照，并共同为第\ref{chap:framework}章 Auto-Evol 统一框架的抽象提供模块级原型。

\section{任务定义与核心挑战}
随着移动端与桌面端用户界面智能体（UI Agent）从“演示原型”走向“真实可用”，能否在屏幕上稳定地“看懂控件、点对位置”成为决定其落地价值的前置能力。本节先给出本章关注的两项基础能力定义，再从这两项能力在真实 GUI 场景中暴露出的稳定性问题归纳出三大核心挑战，并据此明确本章的研究目标与方法路线。

\subsection{基础能力：Referring 与 Grounding}
本章关注 UI Agent 感知--决策闭环中两项最基础的视觉--语言能力。\textbf{指代识别（Referring）}要求模型在给定屏幕区域的边界框（Bounding Box, bbox）后，输出该区域控件的功能、文本或属性描述（例如对“在 bbox [10,10,50,50] 区域的控件是什么？”输出“这是搜索按钮”），强调对界面的语义理解；\textbf{视觉定位（Grounding）}则要求模型在给定自然语言指令时，在屏幕截图中定位对应控件并输出其 bbox（例如对“登陆按钮在哪里？”输出“bbox [100,200,300,400]”），强调对界面的精确定位。两者在形式上互逆，共同构成 UI Agent “看懂屏幕--指向目标”的能力底座，也是本章后续数据合成与训练优化的直接监督目标。

\subsection{三大核心挑战}
尽管通用 MLLM 已具备一定视觉理解能力，但在 GUI 垂直领域同时稳定输出 Referring 与 Grounding 仍存在三大核心挑战。挑战一是细粒度定位偏差：移动端与桌面端控件多以小面积图标、密集排布的列表项与紧贴布局的开关/按钮形式出现，模型需要在像素级输出稳定的坐标，但小目标的 bbox 容易出现“整体方向对、像素级偏移大”的情况，导致 IoU 严重下降。挑战二是图片信息损失严重：若直接将原图缩放到视觉编码器的固定正方形输入（如 $224\times224$ 或 $336\times336$），细小图标与字体被压缩后趋于同质化，进而表现为 OCR 失效、视语对齐变弱与定位偏差扩大，这一损失在中文移动端竖屏场景尤为显著。挑战三是视觉与语言难以对齐：传统检测模型缺乏语义理解能力，而通用视觉语言模型在“标签--输入框”、“值--控件”、“关闭按钮--广告容器”等跨控件关系上往往绑定不稳，呈现“看似可点但不可点”、“识别正确但点错位置”等结构性误差。这三类挑战共同决定了：仅靠通用 MLLM 的零样本能力不足以覆盖真实 GUI 场景，必须在数据、架构与训练三个层面同时引入针对性的设计。

\subsection{研究目标与本章路线}
为应对上述挑战，本章提出一套以多源数据工程为核心、结合双阶段混合微调（Dual-Stage Mixed Tuning, DMT）与高分辨率架构优化的系统方案，目标是在移动端 GUI 最流行前 200 应用的真实使用场景测试数据中实现 Referring 准确率 $\ge 90\%$、单控件 Grounding 准确率 $\ge 90\%$。为帮助读者快速把握“挑战 $\rightarrow$ 方法 $\rightarrow$ 量化验证”的完整对应关系，表\ref{tab:gui_challenge_map}给出本章核心问题、本文方法（创新点）与对应实验结果的总览；后续将按“数据工程$\rightarrow$架构与训练$\rightarrow$实验验证”的顺序逐一展开。

\section{本章核心方法概览}
\label{sec:gui_method_overview}
针对前述 GUI 三大挑战（细粒度定位偏差、图片信息损失、视语对齐松散）与配套的能力冲突/数据冗余等工程难点，本文从“数据 + 架构 + 训练”三个维度共提出 6 项关键技术，统一构成第\ref{chap:gui}章的核心创新点。这 6 项技术在前述表\ref{tab:gui_challenge_map}已与挑战与实验形成一一对应，本节进一步用一段文字把它们浓缩为可被快速检索的“方法卡片”：

\begin{itemize}
  \item \textbf{C1·三类训练任务联合监督}（数据侧）：同时构造 Task Grounding（指令$\rightarrow$bbox）、State Transition（截图对$\rightarrow$状态变化判断）与 Referring 双向 QA（bbox$\leftrightarrow$语义描述）三类训练任务，打牢“语义--定位--状态”三条能力链路，且 Referring 与 Grounding 在形式上互逆，可相互强化视觉--语言对齐稳定性。
  \item \textbf{C2·23 类细粒度控件分类学}（标注规范）：剔除 CARD\_VIEW / LIST\_ITEM 等强布局相关类别，遵循“原子粒度优先”原则，构建覆盖移动端原子交互、复合容器与动态调整三大类的 23 类核心控件体系，显著降低类别歧义。
  \item \textbf{C3·控件有向关系图谱}（标注规范）：在传统“类别+坐标”基础上额外标注三类有向关系——$R_{ext}$（标签$\rightarrow$控件）、$R_{val}$（值$\rightarrow$控件）与 $R_{func}$（功能依赖），显式建模“用户名输入框”等跨控件语义绑定，缓解视语对齐松散。
  \item \textbf{C4·三元交互状态向量}（标注规范）：为每个控件附加 Activated / Interactable / Filled 三元状态信号，区分“看似可点”与“真可点”、“已填写”与“待输入”等关键状态，避免误监督。
  \item \textbf{C5·AnyRes 与 1000 级坐标量化}（架构）：视觉侧采用 AnyRes 动态分辨率机制（全局缩放 + 自适应网格切分 + Patch 位置编码 + 特征融合），同时给出全局视野与局部细节；语言侧把 bbox 坐标统一离散化到 $0\text{--}999$ 整数区间，配合 \texttt{<|box\_start|>} / \texttt{<|box\_end|>} 等特殊 Token 约束输出结构，实现跨分辨率泛化与可解析坐标生成的统一。
  \item \textbf{C6·DMT 双阶段混合微调}（训练）：阶段一用 100\% GUI 数据完成领域知识注入；阶段二引入 80--85\% 通用多模态对话数据，并按 15--20\% 比例回放阶段一的高质量 GUI 样本，同时缓解能力冲突与灾难性遗忘，避免单阶段微调下“GUI 强但通用退化”或“通用强但 GUI 遗忘”的两难。
\end{itemize}

上述 6 项技术之间并非孤立——C1--C4 共同构成数据侧的“高密度结构化监督”（多源数据 + 三件套标注规范 + 三类训练任务），C5 解决了模型如何“看清”并“输出”高密度监督，C6 解决了模型如何在不丢失通用能力的前提下“吸收”这些 GUI 监督。这一“数据 $\rightarrow$ 架构 $\rightarrow$ 训练”的三段式设计，是本章方法体系的统一脉络，亦是后续第\ref{chap:framework}章 Auto-Evol 框架将其归并到统一的“结构化初始化 + 任务原子化 + 多维校验 + 闭环迭代”骨架时的实证起点。

\section{数据工程：多源融合与高质量构建}
数据是GUI理解能力提升的基石。本节围绕“多源融合”与“高质量构建”两条主线，构建开源清洗数据、闭源精标数据与合成数据相互补位的训练语料体系，以保证数据质量可控、可迭代。

\subsection{GUI数据构造流程}
GUI领域的Referring与Grounding能力提升，本质依赖于“理解语义且精准定位”的数据监督：模型既要学会控件的语义功能（登录/搜索/关闭等），又要学会在高分辨率、密集布局中输出像素级稳定的定位结果。相比自然图像，GUI场景存在小目标密集、文字依赖强与交互状态多变等特点，其中“文字依赖”指的是：移动端控件种类多样、外观相似但功能多变，大量关键语义（如“登录/下一步/同意/关闭”以及输入框的字段含义与提示信息）主要通过界面文字表达，必须借助截图中的文本信息（OCR）才能准确判断控件身份与动作目标。使得简单的图文对或粗粒度检测标注难以覆盖真实需求。因此，为了切实提升模型的GUI场景下的能力，本节提出了一种可以处理多种开源数据，同时通过重写、人工精标的方法来构建高质量数据的数据构造流程。

整体流程可概括为“收集多种源数据$\rightarrow$结构化初始化$\rightarrow$混合标注与属性补全$\rightarrow$清洗与结构化聚合$\rightarrow$任务/QA数据合成与过滤$\rightarrow$质控与迭代”。图\ref{fig:gui_pipeline}给出了该流程的可视化全景：从多源输入（开源/闭源/合成）经过四个阶段（结构化初始化$\rightarrow$人机协同混合标注$\rightarrow$三类QA合成$\rightarrow$质控+二级去重）后，输出可用于 AnyRes + 文本化坐标 + DMT 训练策略的高质量训练语料，且质控阶段的失败样本会回流到混合标注阶段继续优化，形成闭环。

下面分模块说明其必要性。收集多种源数据是流程的起点，决定了后续数据分布的上限：为覆盖真实分布与长尾场景，数据来源同时包含开源 GUI 样本（提供多样布局先验）、闭源真实 App 截图（补齐中文与主流应用生态），并视需要引入合成/重写样本以补足稀缺交互形态与困难指令表达。本文实践中，开源侧主要收集并清洗重构了 Rico、MobileViews、OS-Atlas 等数据，闭源侧则面向主流 App 采集真实操作截图并迭代构建高质量自有数据集。结构化初始化承担“图像$\rightarrow$中间表示”的转化任务，将不同来源样本统一为可计算、可追溯的结构化记录（截图、分辨率、视图层级、候选控件集合等），并规范坐标表示与字段定义；为保证不同分辨率设备与不同数据源之间的可混合训练性，本文进一步设计了统一的动作空间，并将所有 bbox 坐标做一致的离散化归一（即 1000 级量化，将像素坐标映射到 $0\text{--}999$ 的整数区间），使“点击/框选”等动作目标能够以统一格式被标注、生成与解析。混合标注与属性补全围绕控件级 bbox 与文字内容进行高质量标注，并补充可交互性与状态等属性，通常采用“检测 + OCR + 属性预测”的自动化预标注，并由人工校验与补充兜底；该步骤同时回应 GUI 三大难点：通过紧致 bbox 缓解小控件定位偏差，通过 OCR 字段解决文字依赖，通过状态/可交互标签避免“看似可点但不可点”的误监督。任务/QA 数据合成与过滤在结构化标注与控件集合基础上生成面向训练的指令/问答数据，本文据此构造 Task Grounding（“指令+截图$\rightarrow$目标 bbox”）、State Transition（“截图对$\rightarrow$状态变化判断”）与 Referring 双向 QA（“bbox+截图$\rightarrow$语义描述”）三类训练任务，将能力同时拆解到感知、理解与状态三条链路上；并通过规则过滤与相似度去重降低噪声与冗余。质控与迭代是闭环的“收尾与起点”：对样本进行一致性与正确性检查（bbox 合法性、OCR 与文本一致性、指令与目标控件匹配、关系图完整性），并将失败样本回收为后续补标/重写/再采集的候选，从而保证数据分布稳定、降低噪声与抑制幻觉。

需要强调的是，上述流程虽然并非后续章节提出的多模态数据合成框架，而是从GUI任务需求出发的一种可行数据工程路径：它首先明确了GUI训练数据必须同时覆盖语义与图形定位，并以“结构化初始化--精细标注--任务化构造--质控迭代”为核心步骤，为后续提出更通用的多模态数据合成框架奠定基础。

\subsection{开源数据清洗与重构}
开源数据在规模与多样性上具备优势，但往往存在噪声、布局失真与语义标签不一致的问题。以 RICO 为代表的 GUI 数据集\citep{deka2017rico}包含大量移动端界面及其视图层级（View Hierarchy），然而原始数据中存在不可见节点、错误标注、层级断裂等现象，直接用于训练会导致模型学习到错误的几何与语义先验。本文采用 CLAY（Clean Layout for Android UI）思路对 RICO 进行清洗与增强\citep{li2022clay}，主要包含三方面工作：一是噪声过滤与层级修复，剔除包含“INVALID”标签、尺寸为 0、透明不可见等节点，并修复视图树结构，确保层级关系可用于后续关系建模与样本构造；二是语义标签映射，将原始 Android View 类名映射为更具语义的通用组件类别，以减少类别碎片化带来的学习难度，例如将 \texttt{android.widget.\allowbreak EditText} 及其子类统一映射为 \texttt{TEXT\_INPUT}，将 \texttt{FloatingActionButton} 映射为 \texttt{BUTTON}；三是任务 Prompt 构造，在清洗后的结构化数据上生成标准化监督样本——Grounding 任务以自然语言指令（如“点击右上角的搜索图标”）与页面截图为输入、输出归一化 bbox，Referring 任务以 bbox 与页面截图为输入、输出组件类别、功能与可见文本（可结合 OCR 字段）。

通过上述处理，开源数据为模型提供了覆盖广的 GUI 布局先验与基础交互语义，但在中文场景、复杂交互与状态理解上仍存在缺口，需要闭源数据与合成数据补齐。除 RICO 外，本文在开源侧还引入了 MobileViews\citep{gao2024mobileviews}与 OS-Atlas\citep{wu2024osatlas}两类 GUI 数据以补齐交互覆盖与定位监督。MobileViews 是面向移动端智能体与 UI 分析的大规模数据集，其 MobileViews-600K 版本包含从 Google Play Store 上两万余应用采集的 60 万级“屏幕截图--视图层次结构（VH）”配对数据；最新版本基于 DroidBot 并针对大规模采集进行了优化\citep{droidbot}，在保持与 DroidBot 输出结构一致的同时能够捕获更全面的交互细节，本文利用其控件类型与组成信息（包括 bbox 与控件内文字）构造训练样本，将控件文字作为 OCR 监督与 Referring 依据，并将 VH 中的层级与控件类型作为语义先验，增强模型对复杂页面结构的泛化能力。OS-Atlas 主要提供 GUI Grounding 数据集\citep{wu2024osatlas}，其中目标元素位置存储在 \texttt{bbox} 字段，采用 $[left,\,top,\,right,\,bottom]$ 的归一化小数表示（每个值均为 $[0,1]$ 范围内相对图像宽高的比例）；在任务构造时，本文将其与其它数据源统一到一致的坐标表示与字段规范（并保持 bbox 的几何语义一致），用于补强“指令$\rightarrow$目标控件位置”的 Grounding 监督，尤其覆盖长尾指令表述与跨应用布局差异。

\subsection{闭源数据构建}
针对开源数据在中文语境、主流App生态与复杂交互状态覆盖上的不足，本文构建闭源高质量GUI数据，并按迭代版本记为v1与v2：其中v1用于早期验证与规范冷启动，重点覆盖文本输入、开关、弹窗等高频交互组件；v2在v1基础上进行二次校验，剔除定义不清的控件并加入负样本（不可点击区域/误导性区域），以提升Grounding的判别能力。闭源数据构建强调“可训练”与“可评测”的一致性：既提供控件级几何定位监督，也提供可解释的语义与状态监督，并进一步产出可用于指令学习的UI意图问答数据。

\paragraph{第一阶段：数据标注（混合标注模式）}
该阶段从原始截图开始（可选携带页面 XML/VH 等元数据），采用“自动化预标注 + 人工校验补充 + 纯人工兜底”的混合模式以兼顾效率与准确性。具体而言，先由轻量检测模型（如 YOLO\citep{redmon2016yolo}）自动检测图标、按钮、输入框等控件并输出 bbox；接着对候选框区域使用 PaddleOCR 提取控件文字（如“登录”“取消”等）形成文字与位置的对齐监督\citep{du2020ppocr}；随后利用已训练的多模态模型（如 Qwen2-VL）对候选控件进行属性补全，包括控件细分类别、可交互性以及选中/开启等状态\citep{bai2025qwen25vl}。最后由标注人员对预标注结果进行校验与修正，并补充模型遗漏的控件；对于复杂样本走纯人工标注分支，最终合并得到统一标注结果，确保每个关键控件的 bbox（位置）、类别（类型）与属性（文字/状态/可用性等）准确一致。OCR 增强是闭源数据的重要补强环节：为降低通用 OCR 在艺术字体与复杂背景下的误识别与“幻觉”，本文引入更高精度的文本抽取与校验流程，生成用于训练的高质量中文文本标注，从而让模型在 Referring 任务中能够稳定对齐“控件外观--文字内容--交互语义”三者。

\paragraph{第二阶段：数据清洗与结构化}
该阶段对标注结果进行质控与格式转换，生成训练友好的结构化数据表示。质控环节首先进行质量校验，检查 bbox 合法性、OCR 文本异常（如过长/乱码）、属性冲突（例如“不可交互但标为可点击”）以及控件间的关联关系是否合理；随后进行数据提纯与聚合，生成包含控件类型、属性、bbox 的纯净样本，并以图片为单位聚合为控件列表（每张截图关联一个包含其所有 UI 元素的集合）；最后通过格式转换将结构化控件集合转换为多种下游格式，以支持指代理解（ref）、定位落地（grd）、列表/容器理解（list）等任务的数据构造与训练。

\paragraph{第三阶段：QA 数据合成与过滤}
该阶段是将结构化控件信息转化为可监督、可解析的训练样本的核心步骤。本文生成的 QA 主要对应三类任务：Task Grounding QA 以“自然语言指令+截图”为输入、输出目标控件的 bbox（与前述 grounding 监督一致）；State Transition QA 以两张连续操作截图为输入、围绕界面状态变化提出问题并给出可验证答案（例如“哪个区域从不可交互变为可交互/哪个开关状态发生变化/页面是否跳转至新状态”等）；Referring QA（反向 QA）以“bbox+截图”为输入、输出目标控件的类别/功能/文本等语义描述，从而与 grounding 形成形式上的双向对应（指令$\leftrightarrow$目标控件描述），增强视觉--语言对齐的稳定性。具体生成时，将聚合好的控件信息与精心设计的系统提示（sys prompt）及少样例（few-shot examples）结合，调用强多模态模型（如 GPT-4o/Qwen2-VL）进行半结构化生成\citep{openai2024gpt4o,bai2025qwen25vl}，并对输出格式（如 bbox 整数坐标、答案可核验字段）施加约束，保证样本可直接用于训练与自动化质检。

为保证质量与覆盖，进一步执行数据过滤与去重。噪声过滤基于规则（如问题过短、答案无意义、指令与目标控件不匹配等）剔除低质量样本。近重复去重则针对 GUI 数据中“同一页面多次采集/相似布局跨应用复现/连续帧高度相似”等现象——这些现象会让样本在训练中被重复计数，既浪费 token 预算也会放大高频模式、挤压长尾覆盖。为此本文采用分层近重复去重策略：

\begin{itemize}
  \item 一级粗去重（精确重复）：对截图（以及 State Transition 中的“截图对”）计算文件哈希或感知哈希，直接移除完全相同或几乎不变的重复帧，先消除采集与导出造成的显式重复。
  \item 二级近重复（语义/布局相似）：为每张截图提取全局视觉表征向量（image embedding，即将整张界面输入预训练视觉编码器，取其池化后的 $d$ 维特征并做 $L_2$ 归一化得到 $\mathbf{e}\in\mathbb{R}^d$），并结合结构化信息构造轻量“页面指纹”（OCR 文本集合、控件类型直方图与归一化 bbox 布局摘要）；候选近邻检索同时考虑视觉相似度与页面指纹相似度，视觉相似度由余弦相似度 $s(\mathbf{e}_i,\mathbf{e}_j)=\mathbf{e}_i^\top\mathbf{e}_j/(\|\mathbf{e}_i\|\|\mathbf{e}_j\|)$ 计算（向量已归一化时等价于内积），页面指纹相似度由文本重叠率/直方图距离/布局摘要距离等组成；只有当两者均高于阈值时才判定为近重复并合并，以避免“视觉相似但语义不同”（如不同商品/不同表单字段）的误删。
  \item 保留策略（避免过度裁剪）：对每个近重复簇保留代表样本，并优先保留覆盖不同指令表述/不同目标控件/不同状态变化类型的 QA；对于 State Transition 任务以“截图对”为单位去重，避免仅按单帧去重导致关键信息（变化前/变化后）被破坏。
\end{itemize}

除上述三阶段流程外，针对闭源数据本文还建立了一套标准化的平台屏幕控件标注规范。该规范不仅关注视觉边界（bbox），还显式引入控件分类学、控件关系图谱与状态向量，从而为 Referring 提供可解释的语义监督信号，并为 Grounding 提供“可交互目标”的判别依据。

\paragraph{细粒度控件分类学（Taxonomy）}
首先构建了覆盖移动端原子级交互单元与容器级逻辑单元的 23 类核心控件体系，遵循“原子粒度优先”原则，以减少布局强相关类别造成的歧义。整体可分为三大类：\textbf{原子交互类}（Atomic Interaction）涵盖 BUTTON、ICON、TEXT、IMAGE 以及输入与开关类（如 TEXT\_INPUT、SWITCH）等原子化交互元素；\textbf{复合容器类}（Composite Containers）涵盖 NAVIGATION\_BAR、TAB\_BAR、CONTAINER、POPUP、ADVERTISEMENT、NOTIFICATION 等承担布局与逻辑分组职能的容器；\textbf{动态调整类}涵盖 SLIDER、PROGRESS\_BAR 及其区域类控件等需要随用户操作而连续变化的控件。在该规范中，剔除了 CARD\_VIEW、LIST\_ITEM 等布局强相关类别，转而采用“原子粒度优先”的原则，以减少模棱两可的布局标注，并促使模型更关注交互本质。

\paragraph{语义关系建模（Directed Relationship Graph）}
传统检测仅预测类别与坐标，缺乏对控件间逻辑的理解。为此，该规范在标注中显式构建控件间的有向关系图（Directed Relationship Graph），该信息对 Referring 尤为关键。本文定义三类有向关系：\textbf{标签--控件绑定}（Label-to-Control）记为 $R_{ext}=(T_{label}\rightarrow C_{target})$，例如输入框左侧的“用户名”文本被标记为外部注释并指向对应的 \allowbreak TEXT\_INPUT，使模型能够更稳定地理解“点击输入用户名的位置”这类指令；\textbf{值--控件绑定}（Value-to-Control）记为 $R_{val}=(T_{value}\rightarrow C_{target})$，例如输入框中已填写的“张三”、下拉框当前显示的“北京市”被标记为当前值并指向父控件，辅助模型区分“输入/修改/清空”等意图；\textbf{功能依赖}（Functional Dependency）描述控件间的功能关联，例如广告弹窗右上角的“关闭（X）”图标与 ADVERTISEMENT 容器建立依赖关系，使模型学习“如何关闭弹窗/广告”这类意图导航。

\paragraph{多维属性与状态向量（Attributes \& State Vectors）}
为支持 UI Agent 决策，本文为每个 bbox 附加多维属性与交互状态信号，核心是一个交互状态三元组：\textbf{Activated} 标注开关开启、Tab 选中、单选框勾选等状态；\textbf{Interactable} 区分可交互与置灰不可交互控件；\textbf{Filled} 标识输入框/选择器是否已有内容，辅助判断执行“输入”还是“修改”。此外，对于 ICON 类补充图标释义（结合上下文填写象形含义，如“房子$\rightarrow$主页”），并对 BUTTON/TEXT\_INPUT 记录内部文本，用于增强视觉编码器与文本空间的对齐目标。

\paragraph{人机协同标注与一致性校验（Human-in-the-Loop）}
为保证标注效率与精度，采用了半自动化标注工作流：OCR预处理生成文本bbox与内容，检测模型生成候选控件框，属性预测模型补全类别与状态；标注员进行校验与微调，并引入一致性检查机制（例如外部注释必须有指向目标、关系图无孤立节点、bbox紧致且合法），以降低噪声样本对训练的负面影响。

\section{模型架构与训练策略}
在数据工程基础上，本文进一步从架构与训练两方面优化模型的高分辨率感知与坐标生成能力，以满足GUI小目标定位与中文文本识别的需求。

\subsection{视觉编码器与分辨率自适应：AnyRes机制}
GUI截图包含密集文字与小图标，且移动端屏幕常呈现高长宽比（竖屏）。若直接将原图缩放到视觉编码器的固定正方形输入（如$224\times224$或$336\times336$），会产生不可逆的信息损失：细小图标与字体被压缩后趋于同质化，导致Referring依赖的文本语义对齐变弱、Grounding需要的像素级几何细节丢失，进而表现为定位偏差与相邻控件混淆。

为此，本文采用动态分辨率（AnyRes）机制（参考 InternVL-2 等工作中的高分辨率视觉输入处理思路\citep{openGVLab2024internvl2}），其核心思想是同时提供全局布局视野与局部高分辨率细节，并将二者的视觉特征统一送入语言模型。具体而言，先对原始截图进行全局缩放（Global Resize）生成一张缩放后的全图，用于捕捉导航栏、内容区、弹窗遮挡等全局布局关系，提供稳定的页面结构先验；然后依据原图长宽比自适应选择网格（如 $1\times2$、$2\times2$ 或 $2\times3$）进行网格切分（Grid Cropping），在原始分辨率空间切分得到多个局部 Patch，每个 Patch 再缩放到视觉编码器的合适输入尺寸，使编码器能够清晰感知按钮文字、图标边缘与细粒度状态差异；为避免“看清局部但不知道其在整屏哪里”的问题，再为每个 Patch 附加其网格索引/相对位置编码（Patch Position Encoding），使语言模型在推理时能够对齐“局部细节$\leftrightarrow$全局位置”；最后分别提取全局图与各局部 Patch 的视觉特征序列并在 Embedding 层进行拼接（或按顺序组织后拼接）作为统一的视觉 token 输入语言模型，使模型既能利用全局图理解页面结构，又能从局部 Patch 读取细小文字与图标细节，从而同时提升语义理解与精确定位。

AnyRes带来的主要代价是视觉token数量增加，从而提升计算开销。本文在网格数量选择上遵循“足够看清关键细节”与“控制推理成本”之间的折中：在典型竖屏场景下优先采用少量Patch覆盖主要区域，以在可接受的计算预算内显著提升Grounding稳定性与中文OCR相关的Referring准确率。

\subsection{坐标表示与定位Token设计：文本化坐标生成}
为充分利用自回归语言模型的生成能力，本文采用文本化坐标表示，将bbox输出为$0\text{--}999$范围的归一化整数序列（即1000级离散化，如\texttt{<box>250,500,\allowbreak ...</box>}）。同时引入\texttt{<|box\_start|>}、\texttt{<|box\_end|>}、\texttt{<|ref\_start|>}等特殊Token，区分普通文本生成与定位任务生成，降低坐标串与自然语言串的混淆。

其中，坐标归一化的目的在于消除不同设备分辨率与长宽比带来的尺度差异：将像素坐标映射到固定范围后，模型学习到的是“相对位置与相对尺寸”的几何概念，而非对某一固定分辨率的硬编码记忆。这使得同一指令在不同屏幕尺寸（例如$1080\times1920$与$1440\times2560$）下仍能输出一致的定位结果，并便于与数据工程中来自不同来源的数据（开源/闭源/合成）进行统一标注与混合训练。同时，使用整数文本序列输出坐标可避免额外回归头设计，并与语言模型的离散生成框架天然兼容。

特殊Token的引入则承担“结构化约束与可解析性”两项作用：一方面，\texttt{<|box\_start|>}、\texttt{<|box\_end|>}等标记显式划分坐标片段的边界，减少模型将坐标数字与自然语言混写导致的格式错误；另一方面，这类标记使下游系统能够以确定性规则解析模型输出，将bbox作为可执行的动作目标（例如点击/框选），从而降低“输出不可用”带来的失败率。对于训练而言，特殊Token也相当于为定位任务提供了更清晰的任务提示（task delimiter），有助于缓解定位生成与对话生成之间的干扰，提升坐标生成的稳定性与一致性。

\subsection{双阶段混合微调（DMT）：GUI注入与通用对齐}
为兼顾 GUI 能力与通用对话推理能力，本文采用双阶段混合微调（Dual-stage Mixed Tuning, DMT）策略\citep{bai2025qwen25vl}。该策略的出发点是：当模型同时学习“专用能力”（GUI 定位、OCR 密集对齐）与“通用能力”（多模态对话、指令遵循与推理）时，简单的多任务混合训练往往会引发两类问题：在数据量较大或任务差异较大时容易出现能力冲突（不同任务目标相互干扰，导致某些能力不升反降）；若采用顺序微调，模型又容易发生灾难性遗忘（后续通用对齐覆盖掉前期学到的 GUI 定位能力）。DMT 通过“先专用、再混合回放”的方式，在两者之间取得平衡。

\textbf{阶段一：GUI 领域知识注入}（Domain Adaptation）。训练数据 100\% 为 GUI 相关数据（开源清洗数据 + 闭源精标数据 + OCR 密集任务），以 bbox 预测与文本对齐为主；训练中冻结视觉编码器大部分参数，重点微调语言模型部分，使模型快速获得稳定的屏幕元素感知与坐标生成能力。\textbf{阶段二：通用能力恢复与对齐}（General Alignment）。在保持 GUI 能力的同时引入通用多模态对话数据（约 80--85\%），并按混合比例 $k$ 回放阶段一的高质量 GUI 样本（约 15--20\%）。$k$ 的取值需要权衡灾难性遗忘与能力冲突：$k$ 过低则定位精度回落明显，$k$ 过高则通用对话与推理能力受到过强 GUI 偏置；本文实践表明，回放比例稳定在 15--20\% 区间即可在保持定位精度的同时不显著损伤通用能力。

从数据混合角度看，已有研究表明：在低资源条件下，多源数据混合可能带来协同效应；而在高资源条件下，简单扩大混合数据总量更容易触发能力冲突，且性能退化往往更多来自“数据总量与任务差异”的叠加，而非比例本身。因此，阶段二采用“通用为主、GUI 少量回放”的设计：一方面继续提升通用对话与推理能力，另一方面用比例 $k$ 的 GUI 回放样本提供持续的定位与 OCR 对齐约束，显式缓解遗忘。同时，相比直接多任务学习，DMT 更能保留通用能力；相比纯顺序微调，DMT 又能通过回放显著降低专用能力遗忘，从而实现 GUI 专用能力与通用能力的更优折中。

\section{实验与评估}
\subsection{评测任务与指标}
围绕 Referring 与 Grounding 两项核心能力，本文采用控件级评测作为主要指标。Referring 准确率定义为：给定目标 bbox，模型输出的类别/功能/文本描述与标注答案一致的比例；对于含 OCR 文本的样本，额外关注关键实体与短语的匹配正确率。Grounding 准确率定义为：给定自然语言指令，模型预测 bbox 与标注 bbox 达到预设重叠阈值（如 IoU$\ge\tau$）且命中目标控件的比例；同时统计在密集小控件场景下的误差分布（偏移量、误命中率）。

其中，IoU（Intersection over Union）用于度量预测框与标注框的空间重叠程度，定义为两者交集面积与并集面积之比：
\[
\mathrm{IoU}=\frac{\mathrm{area}(B_{\text{pred}}\cap B_{\text{gt}})}{\mathrm{area}(B_{\text{pred}}\cup B_{\text{gt}})}\in[0,1].
\]
在 GUI 场景中，许多控件（如图标、页面指示器、滑块把手）尺寸较小且相邻密集，轻微的像素级偏移就可能导致 IoU 显著下降。因此本文同时报告不同阈值下的结果：较宽松的 IoU$\ge$0.1 更关注“是否命中正确控件区域”，而更严格的 IoU$\ge$0.5 则更强调框的几何精确度与边界贴合度。评测样本覆盖前 200 应用的高频页面与交互组件，包含中文文本、弹窗浮层与多状态控件等困难模式，以检验模型在真实分辨率与真实布局下的泛化能力。

\subsection{实验结果与分析}
为验证多源数据工程的有效性，实验设计主要从数据维度进行对比：开源清洗数据、闭源精标数据及其组合（并配合负样本、关系图谱与状态向量等监督信息）。

表\ref{tab:gui_data_ablation}从数据维度汇总了不同数据配置下的Grounding与Referring性能。可以看到，仅使用基线模型时两项指标均较低；引入开源清洗数据后，Grounding F1从0.324提升至0.557，Referring F1从0.523提升至0.612；进一步在开源数据基础上叠加闭源精标数据后，Grounding F1达到0.846，Referring F1达到0.905，两项指标均获得显著累计提升。需要说明的是，本表为“基线$\rightarrow$+开源$\rightarrow$+开源+闭源”的累加式消融，因此第三档的增益反映的是闭源精标数据对覆盖与质量的整体补足，而非“融合”这一动作本身的单独收益；后续若有条件单独评估“基线+闭源”配置，可进一步分离两类来源的贡献。

\section{本章小结}
本章面向移动端GUI这一“控件密集、文字细小、状态易变”的垂直场景，提出了一套提升视觉语言模型屏幕理解能力的系统方案，围绕Referring与Grounding两项核心能力给出从数据到训练的完整落地路径。本文的主要工作与贡献可概括为：
\begin{itemize}
  \item 多源数据工程Pipeline：从任务需求出发构建“收集$\rightarrow$结构化初始化$\rightarrow$混合标注与属性补全$\rightarrow$任务/QA生成$\rightarrow$质控迭代”的数据流程，融合开源清洗数据（RICO/CLAY、MobileViews、OS-Atlas）\citep{deka2017rico,li2022clay,gao2024mobileviews,wu2024osatlas}、闭源精标数据（v1/v2）与必要的合成/重写样本，兼顾分布覆盖与质量可控，为GUI能力持续迭代提供数据基础。
  \item 面向可解释语义与可执行定位的标注规范：提出细粒度控件分类学（23类核心控件）、有向关系图谱（如标签--控件绑定、值--控件绑定与功能依赖）以及多维属性与状态向量（Activated/\allowbreak Interactable/\allowbreak Filled、图标释义、内部文本等），并通过人机协同与一致性校验降低噪声，显式缓解GUI中的语义歧义与“看似可点但不可点”的误监督问题。
  \item 高分辨率感知与坐标生成训练设计：采用AnyRes分辨率自适应机制保留全局布局与局部细节，并以文本化坐标与专用Token约束bbox生成的可解析性；结合DMT双阶段混合微调在GUI专用能力注入与通用对齐之间取得平衡，缓解能力冲突与灾难性遗忘。
  \item 系统评测与量化验证：在Top 200应用的真实页面分布上进行控件级评测，给出不同数据配置与细粒度控件/属性维度的结果统计。实验表明，引入开源数据与闭源精标数据可显著提升整体性能（Grounding F1由0.324提升至0.846，Referring F1由0.523提升至0.905），并揭示了密集小控件近邻混淆与文本绑定歧义等关键误差模式，为后续UI Agent的任务规划与执行奠定基础。
\end{itemize}

需要指出的是，本章方法更偏向以高精度、可执行、可校验的像素级监督为核心，强调“看得准、点得稳”的底层能力建设，这使其在GUI垂直场景中效果显著，但也存在两点局限：（1）对图像背后隐含的事实、概念与关系缺乏直接监督，难以覆盖“先识别再检索/回忆、再筛选推断”的知识推理链路；（2）精细标注与状态/关系建模具有较强的领域依赖与成本约束，当任务从GUI扩展到开放世界知识时，仅靠细粒度可执行监督难以在覆盖度与可控性之间取得平衡。基于这一观察，下一章（第\ref{chap:world_knowledge}章）将进一步面向世界知识能力提升，围绕对齐可信度与推理密度构建更可扩展的数据组织与增强策略，为后续统一的数据合成框架抽象奠定实践基础。
